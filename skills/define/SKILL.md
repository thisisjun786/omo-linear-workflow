# OI Define

Make the intended change clear enough to decide whether and what to plan. An initiative is a
goal with an observable finish, not a permanent product bucket. Read
[Linear through OMO's native MCP](../references/linear.md) for access and write rules and
[Supervisor, parent and child](../references/roles.md) for what a definition does and doesn't
create. Defining an initiative binds no supervisor and moves no project's ownership; a
supervisor begins only from an explicit designation through `oi-run`.

## Recover the intent

Read the request, accepted decisions, and any existing initiative and linked documents through
the authenticated Linear connector. Reuse stable IDs. Separate the user's words, accepted
choices, suggestions and unresolved assumptions. Inspect product or repository evidence only
where it can change the definition. Don't replace the user's goal with a guessed "real problem".

When an answer could materially change the goal, ask one useful question at a time. Prefer the
consequential hidden premise over a fixed questionnaire; a clear intent needs no interview.
Accept "I don't know", a correction or a stop request and update the working understanding
instead of steering back to a preferred answer.

## Define the goal

Write the definition in the initiative body. Keep it compact:

- The original idea, problem or opportunity, and why it matters.
- The desired change and who benefits.
- Observable success evidence and the condition that finishes the initiative.
- Included scope, explicit exclusions, accepted direction and reasons.
- Candidate contributing projects with their roles and outputs, marked as proposals.
- Considered perspectives, deferred choices and open questions that affect planning.

Don't invent dates, owners, numeric targets, validated demand or user answers. Keep evidence and
assumptions apart, and record unknowns as unknowns. Reuse an existing initiative when the goal
matches; related repositories alone don't establish that. A narrow project or a standalone
issue needs no new initiative.

Use Strategy, Scope, Structure, Skeleton and Surface as lenses, not as Linear levels or
required headings. The definition usually supplies Strategy and high-level Scope; project
planning develops the rest when it becomes knowable. Link a repository contract or research
result from its canonical home instead of copying it into the body.

## Apply and hand off

Advice, exploration and draft-only requests produce a proposal without Linear writes. A request
to define, create or update the initiative in Linear covers that initiative's body, not
automatic projects, issues or a separate document. Read current state before writing, preserve
unrelated content, and read back the ID, body and links. Reconcile an uncertain write before
retrying it.

Return the agreed goal, success evidence, scope, open decisions and source IDs with their
revisions. If both a definition and a plan were requested, continue into
[oi-plan](../plan/SKILL.md) in the same operation with that write scope. Definition-only ends
here. Neither artifact launches a role session, imports a scope snapshot or designates anyone.
